## 閱讀方式與證據範圍

本次只整理文件與 PR 描述，未重新登入後台、未修改正式設定，也未建立測試訂單。下列「已有設定／回讀紀錄」整理自本分支 2026-10-20 的既有操作紀錄，不代表本輪再次確認正式服務。CI 或預覽成功不能替代付款、出貨、代收、撥款或發票驗收。

計畫分為兩個階段：**黑貓宅配 COD 已有啟用紀錄，待完成實單驗收；全家取貨付款仍是後續階段**。原本「等全家選店完成才開 COD」的方案已被先開黑貓宅配 COD 的決定取代。銀行資料、金鑰、商店代號、密碼與付費訂閱由使用者操作；需要實際變更設定或交易的待辦，另行取得授權後執行。

## A. 黑貓宅配 COD：現行設定與驗收

### A1. 已有設定與回讀紀錄

- **COD 開通**：使用者自行提交銀行資料並獲核准，後台可見黑貓、順豐、全家的 COD 圖示。CARE 已新增手動付款方式；母站未在本次紀錄中新增。
- **物流匹配**：CARE 已由簡易模式改為進階模式，設定檔 `shopify-gh2xgs-zf` 由上往下比對：
  1. 平台運送方式包含「全家」→ 全家店到店、自行寄件、寄方付款（後續全家階段使用）。
  2. 運送到台灣 → 黑貓宅急便常溫、上門取件、寄方付款。
  儲存後曾重新載入確認兩條規則與 CARE 綁定；母站及第三間商店未變。
- **同步與回寫**：CARE 已由 Sales Order Paid 改為 Sales Order Created，匯入後仍為草擬；已開啟「已簽收／已到服務點 → 更新 Shopify 為已送達」。實際顧客通知、狀態回寫及重複事件行為須在實單驗收記錄。
- **付款擷取紀錄**：Shopify 為「於結帳時自動執行」，但這個設定不能證明每張信用卡或電子支付訂單都成功付款。出貨前仍須核對每張訂單；尤其 ATM 未付款單不能因已匯入就出貨。
- **Flow 已啟用的條件**：觸發 `Fulfillment event created`，且同時符合 `fulfillmentEvent.status = DELIVERED`、付款方式含 `Cash on Delivery (COD)`、`displayFinancialStatus = PENDING`、`shippingLine.title = 標準`，才執行 `Mark order as paid`。滿 NT$1,500 免運仍使用「標準」名稱。
- **Flow 範圍**：採「等於標準」是當時編輯器可設定的精確條件，不等於所有「非全家」配送方式。新增或改名運費必須重新檢查；未來全家運費不得誤命名為「標準」而落入此 Flow。
- **發票偏好**：PR #70 讓成立但未付款的訂單保存偏好到下單後 120 天；付款並建立發票工作後刪除，取消時也刪除（含 `orders/updated` 帶 `cancelled_at`）。已加 11 項資料庫測試；既有紀錄顯示正式版本 `20261019215834` 已套用，PR #71 同步檔名。

### A2. 付款、代收與撥款的界線（待驗證，不變更既有設定）

現行 Flow 是以黑貓送達事件標記 Shopify 已付款，預期進而觸發 `orders/paid` 與發票流程；**它不是 ShipAny 撥款或銀行入帳通知**。每週／撥款時仍需核對 ShipAny 貨到付款紀錄及實際入帳，不能因 Flow 已標記付款就省略對帳，也不應為同一訂單再次例行標記付款。

已有結帳付款說明寫「電子發票會在貨款結算確認後開立，並寄到您的 Email」，與 Flow 的送達即標記付款時點不一致。此處保留為待處理事項：由使用者確認採用的營運時點、例外處理及發票要求，再另行授權調整說明或流程。本次沒有改付款文案或 Flow，也不宣稱送達事件已證明代收成功、撥款完成或發票已開立。

### A3. 首筆實單前待確認

| 待辦 | 負責人／需要的證據 |
|---|---|
| ShipAny 可實際出單 | 使用者確認預付／月結；若須儲值，由使用者完成。確認物流代收費、實際運費與對顧客收費的安排 |
| 正式發票鏈路 | 使用者確認光貿正式設定與 release；技術人員核對 waaship 是否存在另一條開票路徑，確認唯一責任流程。不能只以環境變數存在認定可用 |
| 送達即標記付款的邊界 | 使用者確認 A2 的付款／結算／發票時點；驗收需確認正確配送事件才觸發，未送達、拒收或取消不會被誤標記 |

以上是待確認／待驗收事項，不能回填為已完成。COD 已有啟用紀錄，本節並非再次啟用的操作授權。

### A4. 黑貓 COD 實單驗收清單（全部待執行）

實單會產生代收、運費與派件；安排前另行取得授權，確認 A3 條件。每一步記錄 Shopify 訂單號、ShipAny 單號、Flow 執行紀錄與時間，避免只用截圖中的單一狀態推論整段完成。

- [ ] 建立一筆配送為「標準」、付款為 COD 的真實訂單，確認尚未付款與結帳發票偏好已保存。
- [ ] 確認依 Sales Order Created **自動**匯入 ShipAny 一次、保持草擬、匹配黑貓 COD，代收金額等於折扣後含運費總額。若未匯入，先查原因，不能未查重就手動重複匯入。
- [ ] 在出單前於 Shopify 修改品項或金額，確認已匯入的 ShipAny 訂單與代收金額跟著更新；只在 Shopify 改單。
- [ ] 出貨前核對付款方式、付款狀態、收件資料及代收金額；非 COD 未付款單不得跟著出貨。確認可建立運單、費用與黑貓取件方式。
- [ ] 確認真實送達事件回寫 Shopify；查看 Flow「近期執行」，四項條件均符合後只產生預期的付款轉換。未送達、拒收／取消、非 COD 及不叫「標準」的配送不應被誤標記；缺少事件覆蓋時記為未驗證。
- [ ] 核對 Shopify 付款狀態、CARE 訂單投影、發票工作及 provider 回讀，確認依結帳偏好開票，並驗證發票 Email；確認付款事件不造成重複匯入或重複開票。
- [ ] 另於 ShipAny 結算／撥款時核對代收紀錄、費用、淨額及實際入帳。已被 Flow 標記付款的訂單不再次例行標記。
- [ ] 若測試需取消退款，確認物流停止／退件、退款及必要的發票作廢／折讓全部完成；處理方式見 C 節，不能把 Shopify 退款成功當成發票已處理。

### A5. 現行日常作業與例外

1. 正常路徑為自動匯入草擬單 → 人工出貨前檢查 → 出單 → 黑貓送達回寫 → 符合條件的 COD Flow 標記付款。`COD` 標籤可供作業辨識，但不是付款證據，也不是目前 Flow 條件。
2. 訂單修改只在 Shopify 進行；出貨前核對 ShipAny 代收金額。匯入或 Flow 失敗列為例外，先查同步／執行紀錄及是否已有運單，不預設必須手動重匯。
3. 每週或撥款時獨立對帳。Flow 未執行的訂單，需先確認實際代收及失敗原因，再依核准作業處理；不以手動標記付款掩蓋未收款或同步問題。
4. 退款、取消、拒收、金額異動、超過 120 天的發票偏好等例外需人工追蹤，不視為現行自動化已完整涵蓋。

## B. 全家取貨付款：後續階段，尚未開放

這一階段不再是黑貓 COD 的啟用前置條件。現有 ShipAny 全家匹配規則只是準備工作；網站仍只宣告黑貓宅配，`scripts/verify-public-content.mjs` 仍限制未開通的超商取貨文案。

| 順序 | 待辦 | 負責人／完成條件 |
|---|---|---|
| 1 | 取得選店方案與 API 文件 | 使用者自行訂閱「物流服務點列表」並申請門市列表／Widget API；依實際文件決定串接及金鑰位置。2026-10-20 附加功能頁曾顯示無可用功能，約 10/30 自助開放只是客服當時預估，未證實可用 |
| 2 | 決定商業規則 | 使用者決定全家運費、滿額免運、COD 手續費、金額上限及未取件處理 |
| 3 | 實作選店與門市驗證 | 技術人員依 ShipAny 規格將門市資料帶入 Shopify Cart／訂單；必須驗證有效門市代碼，缺漏或失效不能完成需門市的配送流程。不能只以配送名稱含「全家」當作已選店 |
| 4 | 設定配送與付款相容性 | 經授權新增名稱含「全家」的 Shopify 運費，確認套用 ShipAny 第一條規則；驗證全家與黑貓切換、COD 金額及門市資料。COD 已存在，不需再新增同名付款方式 |
| 5 | 定義全家付款確認流程 | 不沿用黑貓 `DELIVERED + 標準` 的付款 Flow；「到服務點」不代表顧客取貨付款。依 ShipAny 可提供的實際取貨／收款證據確認人工作業或後續自動化方案，尚未定案 |
| 6 | 真實全家訂單驗收 | 經授權下單後確認自動匯入一次、門市及金額正確；匯入完成後才測試 Shopify 改單同步。驗證到店不誤標已付款、實際取貨付款後的 Shopify／發票處理、未取退件及後續對帳 |
| 7 | 公開配送文案 | 功能與運費準備完成並通過驗收後，才更新 FAQ、商品頁配送標籤、隱私權政策及 `verify-public-content.mjs`；不得只放寬文案檢查而未完成串接 |

**付款規則 app 是備案，不是目前必購項目。** 已確認黑貓也有 COD 開通紀錄，使用者決定先不裝 Payfy。若未來出現不能承接 COD 的運送方式、或現有能力無法防止全家缺少門市資料，才另行評估付款／結帳限制方案；需重新確認 Shopify Basic 相容性、規則能力、權限及費用，經使用者選定後實作與驗證。歷史 Payfy／Easy! Payment Control 等比較及報價不作為目前採購或上線依據。

## C. 正式線上付款與發票：共同待辦

1. **TapPay**：使用者確認正式商家審核、正式金鑰與可提供的付款方式，再授權切換。既有回讀仍為測試模式；信用卡、ATM、街口、LINE Pay 等需逐項確認，不能以結帳可見推定可正式收款。
2. **PayPal**：使用者決定完成設定或暫不提供；本輪不修改。後台設定未完成但結帳可見的矛盾須解除。
3. **光貿及開票責任**：確認正式 seller／key、Vercel 發票 release 設定與 waaship 是否另行開票。只有沙盒證據或敏感環境變數欄位存在，不足以宣稱正式可開票。發票時點、通知與例外處理由使用者確認營運及適用要求；黑貓現行 Flow 與結帳說明的差異見 A2。
4. **真實線上付款驗收**：條件完成並取得授權後，以小額訂單驗證實際付款、Shopify、CARE 訂單與正式發票；退款與取消依使用者決定處理。
5. **發票清理**：取消退款不會自動完成已開立發票的清理。訂單取消可能使工作進入 `void_review`，退款可能另建 `allowance_review`；依實際狀態選擇適當的作廢或折讓流程，經核准 RPC（`approve_amego_invoice_void`／`approve_amego_allowance_issue`）及 worker 派送，再回讀光貿 provider 狀態。不是每筆都執行兩種處理；沙盒 #1008 的做法見 [訪客結帳驗收紀錄](GUEST_CHECKOUT_LAUNCH_CHECKLIST.md)，不代表正式流程已驗收。
