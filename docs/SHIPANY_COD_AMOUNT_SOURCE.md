# ShipAny 逐單代收金額來源與第一筆實單驗收

更新：2026-10-22（Asia/Taipei）。接續 [後台查核](SHIPANY_COD_LIVE_VERIFICATION.md)，處理 ShipAny COD 金額可獨立修改、Shopify 不會反向取得該變更的缺口。本輪完成來源能力調查及接入判準；尚未取得 API schema／授權，沒有部署讀取器或宣稱實單通過。

## 結論與接法

**優先路徑為 ShipAny 官方、具身分驗證的逐單讀取 API，搭配訂單生命週期 Webhook 喚醒查詢。** 查詢對象必須是 Shopify App 已匯入的原運單，不能另建 API 運單替代。收款語意仍以 ShipAny 10/22 黑貓常溫 COD 書面確認為依據，逐單金額則必須改由 ShipAny 的可信運單欄位提供。

這是待供應商確認的接入方向，不是已證實可用的 endpoint。除了讀取「最新表單金額」，還要證明該金額是物流業者接受並在送達時執行的 COD 金額；若送達後仍可任意改寫、無歷史版本或生效狀態，最新值也不能證明當時收足多少。

## 可信逐單證據必須包含的概念

以下為接入需求，**不是 ShipAny 已公布的欄位名稱**。收到官方 schema 才能實作實際映射。

- 來源：正式台灣 API、已驗證帳號／商戶、最小讀取權限；密鑰只在伺服器，不能依賴後台登入 cookie 或未公開內部 API。
- 身分：ShipAny 運單 ID、來源平台／商店及原 Shopify 訂單 ID、黑貓常溫服務精確識別、當前有效託運號；不可只用跨店重複的 #1007 或可任意改寫的參考文字。
- 金額：COD 啟用、TWD、指定代收金額、代收額是否已被黑貓接受／生效；與商品申報價值、物流費、平台手續費及撥款淨額分開。
- 時間與修改：來源更新時間／版本或等價修改履歷、舊託運號撤銷與換單關係、送達前後可否改額；需能辨識送達時實際採用的金額。只由本地加 receivedAt／雜湊不會讓來源變可信。
- 完整性：合併／拆分關係與全部有效貨件、撤回／取消／送達更正。第一階段仍只接受單一完整貨件。
- 通知可信度：官方驗簽規格與防重播；若通知不能驗簽，可在經評估的前提下只作限流後的查詢提示，絕不能用通知內的金額或狀態直接授權付款／開票。

## 程式接入後的行為（尚未實作）

1. 以既有 Shopify 訂單與 ShipAny ID 找原運單；取得官方逐單回應，核對來源商店／平台訂單 ID、服務、託運號及整單品項。沒有官方 shop 欄位時須另外證明可靠跨店隔離方式，不能略過。
2. 出貨前及送達後都即時回讀。只有有效運單的生效 COD 額等於 Shopify 已核對的整筆應收，才繼續檢查 DELIVERED 契約；讀取失敗、金額不同、改額待生效、拆併單、來源不明、版本落後均停止自動操作並補查。
3. 保存最小且不可變的來源證據：運單／託運號、生效 COD 額／幣別、來源版本／時間、物流服務、送達資訊、驗證時間及內容指紋。仍標示「指定代收額直接讀取＋已收足依契約推導」，不可標成獨立實收 API。
4. 首次開票／標記付款前再讀回並比較；證據成立後金額或託運號更正，既有證據不覆寫，進入查核。若來源缺少送達時金額或生效保證，不能只憑最新查單值通過此步。
5. 保留目前 Shopify 簽章事件、DB 去重／lease／取消退款控制及唯一發票工作。ShipAny 原始完整 payload 含個資時不寫入一般 log；前端沒有輸入金額即可放行的入口。

## 第一筆實單前可做的驗收與實單必做項

| 階段 | 通過條件 | 現況 |
|---|---|---|
| 供應商規格 | 確認既有 Shopify 運單可查、生效 COD 額語意、修改版本／鎖定、驗簽、方案範圍 | 已完成精確問題草稿，未寄送 |
| 非交易讀取 | 使用已授權的唯讀憑證查 #1007 原草稿；身分／非 COD／無 tracking 與後台吻合 | 未取得 API 授權，未執行；此筆不能作正向 COD 樣本 |
| 金額變更測試 | 在供應商確認的隔離 sandbox 證明改額／回改／事件亂序／來源失敗均不誤放行 | Shopify App 既有回覆無獨立 sandbox；API sandbox 能力與是否覆蓋同一匯入路徑另待確認。不在舊正式草稿改額製造樣本 |
| 真實訂單草稿 | 非測試 COD、金額含實際折扣與運費；原單匯入後 API 與畫面指定 COD 額相符，任意差異均攔下 | 尚無指定實單 |
| 正式出單 | 核對黑貓接受的最終金額／版本、唯一託運號與 Shopify 履約欄位；先處理舊 Flow／唯一開票來源 | 未出單 |
| 送達收款 | 取得同一託運號的 DELIVERED 與生效 COD 額，完成證據 → 唯一發票 → 通知／存證 → paid 回讀 | 待真實配送完成；不能用模擬結果代替 |

若官方 API／可信通知無法提供上述必要資訊，現有 App 模式不能支持所要求的全自動金額驗證。屆時應請供應商提供受支持的資料／不可變金額回寫，或另外評估直接 API 建單及後續鎖定；這是架構變更，不能默默切換、重複建立運單或改成日常人工核准。
