# SAENGAK 結帳系統與架構升級決策 (ADR)

> 建立日期：2026-08-13
> 決策目標：解決現有 Shopify 結帳系統無法即時鎖定庫存的問題，並整合 SiteGiant ERP 與在地化服務。

> **⚠️ 2026-08-17 修正說明**：本文件第 2 節「庫存鎖定能力」比較表所述之「Vercel API 直連 SiteGiant ERP 進行 Reserve/Commit 鎖定」，已於 `00_DECISION_LOG.md` 廢棄，改為 **SiteGiant Shopify App 雙向自動同步**，以消解 Serverless 逾時與中間態卡死風險。本 ADR 之「自建結帳頁 + TapPay SDK + Vercel 中樞」核心決策維持不變，僅庫存鎖定手段修正；細節以 `CHECKOUT_PAYMENT_SPEC.md` §2 為準，本文件保留作歷史決策脈絡紀錄，不再更新其論述內容。

## 1. 決策背景與核心挑戰

SAENGAK 品牌在正式上線前，面臨一個嚴峻的營運與技術挑戰：**庫存超賣與系統同步問題**。
我們原本依賴 Shopify 原廠的結帳系統 (Shopify Checkout) 搭配其生態系的 TapPay 金流 App。然而，此模式有一個致命缺陷：**我們無法在顧客「準備刷卡」的那一瞬間，與公司的核心庫存系統 (SiteGiant ERP) 進行溝通與鎖定庫存。**

為了確保庫存的絕對精準，並提供符合台灣消費者習慣的超商取貨 (ShipAny) 與自動化電子發票 (光貿)，我們必須對結帳架構進行升級。

## 2. 結帳架構選項比較

技術團隊針對「維持現狀」與「自建結帳」進行了深度的優缺點比較：

| 評估項目 | 舊模式：依賴 Shopify Checkout 跳轉 | 新模式：自建結帳頁 + TapPay SDK (本次決策) |
| :--- | :--- | :--- |
| **庫存鎖定能力** | ❌ **無法鎖定**。受限於 Shopify 封閉流程，無法在刷卡前呼叫 SiteGiant ERP 鎖定庫存，容易引發超賣客訴。 | ✅ **完全掌控**。由我們自建的 Vercel API 發動扣款，可確保「先透過 ERP 鎖定庫存，成功後再扣款」。 |
| **品牌一體性** | ❌ 結帳時顧客會跳離品牌官網至 Shopify 網域，體驗產生斷層。 | ✅ 顧客全程留在 `saengak.com.tw` 網域，購物體驗無縫且專業。 |
| **在地化服務擴充** | ❌ 難以在 Shopify 封閉的結帳頁面中客製化「ShipAny 超商地圖」與「發票載具」。 | ✅ 可在結帳頁面隨心所欲地完美融合超商選店 UI 與發票輸入欄位。 |
| **初期開發成本** | 🟢 極低。直接使用 Shopify 內建功能。 | 🔴 較高。必須自行開發結帳表單、運費計算與 API 串接。 |
| **後續維護責任** | 🟢 金流與訂單同步由 TapPay App 處理。 | 🔴 需自建交易防呆機制，確保金流、Shopify 訂單與 ERP 的狀態完全一致。 |

## 3. 最終決策與商業價值

基於上述評估，管理與技術團隊決議採用 **「新模式：自建結帳頁 + TapPay SDK + Vercel 中樞」**。

這是一項關鍵的基礎建設投資。雖然初期會增加開發工時，但將為品牌帶來深遠的商業價值：
1. **杜絕超賣風險**：確保每一筆扣款背後都有實質的 SiteGiant ERP 庫存支撐，保護品牌信譽。
2. **極致的消費者體驗**：在自有網域完成結帳、順暢選擇超商與發票，預期可大幅降低結帳流失率，提升轉換率 (CVR)。
3. **無上限的擴充能力**：未來若要串接新的行銷工具、紅利積點或新的物流商，不再受限於 Shopify 平台的限制，將系統命脈掌握在自己手中。

## 4. 風險控管與下一步

為確保新架構的高可靠性，工程團隊已在技術規格書中設計了 **分散式交易補償機制 (Transaction_Logs)**。
若發生「顧客扣款成功，但 Shopify 或 ERP 剛好當機無法建單」的極端情況，系統會自動記錄並觸發警報、啟動重試，或是自動通知 ERP 釋放庫存，絕對避免帳務死結。

本決策已正式定案，並納入主規格書中，工程團隊將即刻展開後續的系統重構與開發作業。
